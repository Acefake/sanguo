# 三国策略游戏：大地图实现方案

## 当前全国版接入（2026-10-01）

用户已确认扩展为全国版图。主场景现读取 `data/world_map.json` 和 `data/scenario_world_demo.json`，使用 1920×1080 世界坐标，13 个州区、70 座城池、2 处关隘和 96 条道路。城池节点改为白色盾形；所属势力决定领地、盾牌色带与地图势力名。无主区默认保留灰淡地形，可切换灰白填色。领地分区按城池邻近关系构建，州界独立显示。

下文保留原局部阶段的设计依据。最新素材、数据范围和生成提示词见[全国大地图说明](全国大地图说明.md)。

## 1. 目标与边界

第一版先完成类似《三国志8》的战略大地图：玩家能查看全图、缩放平移、选择城池或关隘、查看所属势力，并沿道路规划移动。地图暂不承担战场内的自由移动；部队在战略层按地点之间的连接行军。这样可以先把内政、外交、战争共用的地理规则做稳。

用户提供的图片只作**构图与美术参考**。当前局部原型已使用原创地形画和独立绘制的州界、道路、节点及文字；图片像素不进入游戏画面，也不承担势力或通行规则。

## 2. 核心选择

- **表现方式：2D 分层地图。** 底图表现山川地貌，上方分别绘制区域色、边界、道路、地点、部队及交互效果。无需 3D 地形或六角格。
- **玩法模型：带权图。** 城池、港口、关隘、渡口等是节点；可通行的道路或水路是边。路线、行军时间、阻断和补给均由图数据决定。
- **区域模型：独立多边形。** 一块区域可以代表郡、州或美术分区，但其含义必须在数据中明确。势力归属根据剧本中的城池控制关系计算或明确指定，不能写死在底图颜色中。
- **坐标：局部切片以 1260×710 为设计坐标系。** 地点与区域存图内坐标，窗口变化时整体按同一比例缩放，避免节点和背景错位。扩展到全国地图时再建立新的统一世界坐标系。
- **默认技术路线：Godot 4 的 2D 场景与 JSON 数据。** 目前目录为空，Godot 可直接支撑桌面游戏原型、地图相机、交互和后续游戏系统。如果未来确定采用别的引擎，下面的数据和分层方式仍可复用。

## 3. 地图分层

从下到上：

1. **背景层**：深色水域、地形纹理、山脉河流和装饰边框。尽量取得没有节点、道路、固定势力色的原始美术图；若只有当前合成图，原型可以先用它，正式版需要重新拆层或重绘覆盖。
2. **区域层**：每个区域一条闭合多边形，半透明填充势力色；边线单独绘制。无主区域采用中性色。鼠标悬停和选中时只改变该层的描边/透明度。
3. **交通层**：道路、水路、桥梁及不可通行的地理线分开保存。显示曲线可贴合原图，实际通行仍由端点和边的属性控制。
4. **地点层**：城池、关隘、港口、渡口等图标、名称、等级与状态。参考图中的白色圆点先作为候选位置，不能在未考证前直接命名为历史城池。
5. **动态层**：部队标记、行军箭头、攻城提示、补给范围、事件标记、战争迷雾。
6. **界面层**：顶部时间/势力信息、右侧地点详情抽屉、悬停提示和地图模式切换。界面不跟随地图缩放。

建议实现上把区域填充和交互热区复用同一组多边形坐标；地点的点击热区可比可见图标大。道路不负责点选时，可关闭其鼠标拦截。

## 4. 数据结构

地图静态数据与剧本数据分开。静态数据描述地理事实；剧本按年份设置势力、人口、驻军、城池等级和道路状态。同一地图可复用多个历史剧本。

| 文件 | 内容 | 关键字段 |
| --- | --- | --- |
| `regions.json` | 州/郡或美术区域的边界 | `id`, `name`, `polygon`, `type`, `city_ids` |
| `places.json` | 城池、关隘、港口、渡口的位置 | `id`, `name`, `type`, `x`, `y`, `region_id` |
| `routes.json` | 地点之间的可通行连接 | `from`, `to`, `mode`, `distance`, `terrain`, `control_point`, `curve` |
| `scenarios/<year>.json` | 特定剧本的动态状态 | `owner_by_place`, `garrison`, `population`, `route_overrides` |

示意数据（坐标和名称仅说明格式，不代表已完成历史校对）：

```json
{
  "places": [
    { "id": "city_001", "name": "待考证", "type": "city", "x": 714, "y": 326, "region_id": "region_01" },
    { "id": "gate_001", "name": "待考证", "type": "pass", "x": 831, "y": 325, "region_id": "region_02" }
  ],
  "routes": [
    { "from": "city_001", "to": "gate_001", "mode": "land", "distance": 1.0, "terrain": "plain", "control_point": "gate_001" }
  ]
}
```

`curve` 只决定道路怎么画；寻路使用 `from/to` 和通行代价。所有 `id` 稳定，不把显示名称作为外键。地点只属于一个基础区域；如果将来存在跨州边界的城市，用独立行政归属字段表示。

## 5. 交互与规则

- **查看**：滚轮以鼠标所在点缩放，按住鼠标拖动平移；缩放范围建议先设 0.8～2.5 倍，镜头始终保留地图边缘。支持“回到全图”。
- **选中**：单击地点弹出详情；单击区域显示区域概况；悬停只做轻量高亮。选中状态始终清楚，缩放后文字按可读性分级显示。
- **地图模式**：地形、势力、行政区、交通至少四种。模式仅改变可视化，不改地理与剧本数据。
- **路径**：从选中的起点选择终点，用 Dijkstra 或 A* 计算最短耗时路线。边代价由距离、地形、道路类型、部队属性和天气修正。关隘受敌方控制时，根据外交/战争状态禁止通过或提高代价。
- **战争**：部队位置记录为节点或边上的进度；封锁、占领和补给只更新动态图/剧本状态。区域颜色通过当前控制情况刷新，不烘焙回地图图片。
- **保存**：存剧本 ID、回合状态、地点与边上的动态值，不保存整张地图图像或重复静态边界。

## 6. 从附件落地的制作流程

1. **锁定设计范围**：按用户附件确定局部五州的构图、可操作范围和 UI 留白；附件始终仅作为参考。
2. **制作原创底图和可编辑图层**：地形用独立画作，区域边界、道路、地点与关隘分别保存为数据和可绘制元素。当前原型已经采用此结构。
3. **建立地点清单**：为每个可玩节点赋稳定 ID、类型与坐标；先只标 `待考证`，再根据选定历史时期考据城名和关系。对照图片逐一检查遗漏、重复点和道路端点。
4. **建立交通图**：每条道路必须连接两个已存在的地点。区分陆路、水路、山道与关隘通路；跨河是否需渡口由数据决定。视觉上交叉的两条路并不自动相连。
5. **接入首个剧本**：先用少量势力与一小片区域检验颜色、选中、通路和占领更新，再录入全图。剧本年份确定后再填历史阵营与城池状态。
6. **美术打磨**：继续修整原创地形、边界曲线和行政区位置，统一文字层级、图标尺寸、缩放级别和选中反馈。

描图工具可以是 Inkscape/Figma 导出 SVG，再通过小型转换脚本导出 JSON；也可以直接在 Godot 编辑器里绘制多边形和曲线。核心要求是保留可编辑源文件，不在代码里手写上百个无出处的坐标。

## 7. 分阶段交付

| 阶段 | 可体验结果 | 完成标准 |
| --- | --- | --- |
| A. 地图浏览 | 打开全图、缩放、拖动、点击测试地点 | 在常见窗口比例下图与点击位置不偏移 |
| B. 真实地图数据 | 区域、全部地点和道路独立成层 | 地点都有唯一 ID；边端点有效；道路与参考图吻合 |
| C. 战略交互 | 地点详情、势力模式、选路和行军预览 | 任意连通地点可求路；封锁关隘会改变路线 |
| D. 剧本接入 | 一个年份的势力与城池数据 | 占领城池后地图颜色和通路状态即时刷新 |
| E. 美术完成 | 可发布的原创分层地图 | 不依赖参考图中烘焙的圆点、道路或势力色 |

第一轮最小可玩切片建议只录入图中央约 8～12 个地点、两处关隘和相连区域，先验证表现与寻路；随后再覆盖全图。这不会限制完整地图的数据格式。

## 8. 需要尽早确定的设计决策

1. **历史范围**：选哪一年或哪些剧本？这决定地点名称、控制势力和道路可用性。
2. **地图粒度**：图中的每个白点是否都要成为城池？建议按历史资料划分为城、关、港、渡口，避免所有节点具有相同功能。
3. **区域含义**：彩色块是州、郡，还是纯美术分区？建议把行政区与势力色分离；同一行政区可以包含不同势力城池。
4. **史地精度**：当前五州边界参考的是视觉构图。正式地图要按目标年份校对州郡、城池和通路，并确定哪些区域应随势力控制改变颜色。

在这些决定落实前，地图浏览和通用数据结构可以先做，地点命名与历史剧本保持可替换。
