# 军团主帅智能体与小沛测试

在主设置打开“小沛中型对战 · 全武将出阵／重置”，点击“进行”执行十日。地图默认使用3D，日期按日结算，地图部队连续播放移动与战斗；可调速度或暂停。已有测试需重置才会使用新编组，正式战役存档不受测试影响。

## 指挥与人物任职

18名人物组成两支军团，双方各20000人，步弓骑70/20/10。按人物资料“位置”的核心、次选和不宜位置及对应能力选择任职：诸葛亮、孙策任主帅，其他人物分别担任副帅、军师、前锋、奇兵、护军或参军。原人物文件和正式势力归属不变，孙策仅在测试中加入对手。

一支军团初始展开中军、两支前军、奇兵和预备队，共五个占格分队。这些是同一军队的编组，不是五支互不相关的军队。每个分队由领队武将执行主帅军令；中军人员参与军团任职与主帅决策上下文。地图数字是该分队兵力，详情另显示军团总兵力，避免重复统计。

模型只负责主帅的战役决策，部将由规则控制器执行任务，不再每人同时请求模型或自行修改战略目标。主帅获得全军任职、分队兵力、士气、组织、携粮、撤退状态及汇总侦察敌情；测试观察者能看到双方，模型不能读取未侦察的敌情。已有独立出征旧存档仍兼容原策略。

主帅可保持部署、调动主攻／侧翼／预备队／掩护队、派现有部队绕后或断粮、拆出500／1000／2000人的独立小队、命令归建或全军撤退。拆队需要本军团未领分队的人员、至少500人留在来源部队以及空闲相邻格；接战中不能通过拆队绕过包围。士兵按兵种从原队转移，携粮按比例转移，不增加总兵力和粮草。归建必须实际回到中军相邻格且脱离接战，才合并兵粮与战损账目。原中军结束任务后由适任领队接掌指挥，全部部队归营后解除随军人员占用。

正常战役出征面板可选择主帅和随军人员，组成军团，并按共同城市道路行军；主帅面板“全军撤退”和军令会传给全部分队。当前绕后、独立断粮和六边格寻路的完整验证场景是小沛战场，全国战役的独立粮道与六边格通行尚未接入。

## 粮道与接战

双方后方有实际粮道格，地图标记畅通／截断状态；镜头外的标记贴屏幕边缘提示。各队携带七日粮，其余随军储备放在粮道；正常配送补至七日粮，消耗仍由既有日结规则计算。

敌方粮道进入任一分队五格侦察范围后，主帅才得到断粮候选。小队逐格走到该粮道相邻格、没有贴身敌军时，实际截断配送四日，并从敌储备转移最多五日小队用粮。三日内不能重复劫粮；储备与所得严格守恒，已携粮不会凭空消失，断粮通过后续消耗产生影响。当前采用粮道节点与配送状态，尚未加入可见运输车队和护送战斗。

绕后小队到达可通行后方目标格后才转入攻击。沿途被接战牵制时不能直接脱离；这不是隐身或瞬移能力。预备队保持军令，主帅可令其补线或掩护撤退。掩护优先接应最近的撤退友军。

近战一格，原远程支援有弓兵时射程三格。六邻格统一用于移动、侦察、射程与夹击。撤退需要1+贴身敌军数日准备，相邻掩护减少一日，最短一日；进入敌军控制格还多需一日，敌军占满六邻格时无法穿越。准备损失组织，撤退承受额外近战压力，成功脱离当天仍承受追击。进攻中的部队也不能随意离开接触，需先收到撤退或归建军令。溃败仍会触发强制保命撤离。

战场使用原版map_grid.bin中小沛附近15×19交错列六边格，配准采用项目现有grid_transform.json；原版运行时坐标常数仍未确认。水域、山地和地图外等地形暂禁止通行，未加入舟船、桥梁。

## 本地模型

本机已安装Ollama及Qwen3 1.7B Q4_K_M。主设置选“本地Ollama”预设，检测服务与模型后保存；无需API Key，旧云端配置不会自动替换。其他Ollama模型可直接改模型名。服务启动与预热：

```powershell
powershell -ExecutionPolicy Bypass -File tools/start_local_agent.ps1
```

使用原生http://127.0.0.1:11434/api/chat，关闭思考，候选ID枚举JSON schema，4096上下文、128输出token，默认一次一个请求、每个游戏日等待上限15秒。主帅平稳时每三日重判，分队退却、通路受阻或粮道截断等变化可提前触发；其余日期直接执行军令。超时、格式或候选错误由本地主帅策略接管。小模型只提出命令，规则决定合法性和实际后果。

真实本机测量保存于[local-agent-benchmark.json](validation/local-agent-benchmark.json)，记录两位主帅批次与连续三日模拟。首次加载、GPU竞争、提示长度和其他进程会影响速度；耗时检查不是战术质量评估。协议依据[Ollama API](https://docs.ollama.com/api/chat)。

## 参战势力与分边

谁参战、谁当主帅写在 data/war/xiaopei_battle.json，代码里不出现势力或人名：

```json
{
  "player_faction": "liu_bei",
  "sides": [
    {"faction": "liu_bei", "role": "defender", "leader": ""},
    {"faction": "yuan_shao", "role": "attacker", "leader": ""}
  ]
}
```

- role：defender 从小沛出发守城，attacker 从濮阳出发进攻，须恰好一守一攻。strengths（battle_scenarios.json）按同一势力 id 取兵力。
- 人物按名册里的势力归边，不改任何人的势力；名册的势力来自人物卡的 faction_id，卡上没有时用 campaign_rules.json 的 faction_mapping 换算 faction 显示名。未声明的势力不参战。
- leader 填人物 id；为空或不在本方时由本方按「主帅」择帅（army_corps.best_member，不在本方会告警）。当前两方都留空，沿用原来的择帅结果。
- 一方没有人物卡武将时，用名册里该势力的生成将（ensure_factions 按剧本补足的“某某·偏将N”等）补位并 push_warning；生成将也没有时 push_error 并不开战。选补位而不是拒绝开战，是因为人物卡换成只有部分势力的剧本（如官渡只有袁、曹两家）时，拒绝会让小沛测试与依赖它的战斗测试全部无法运行；补位的人明确是生成将，不冒充历史人物。

此前分边写死两家：所有非生成武将不是刘备方就划给袁方，并改写其势力。用现在的 18 张人物卡时，孙吴集团的孙策会被划进袁方并改成袁绍势力；换成官渡人物卡后，曹营 10 人被划进袁方、曹操当了袁方主帅，刘备方 0 人，出征时主帅 id 为空而报错。

## 验证

- tests/war/campaign/corps_validation.gd：指挥层级、位置任职、军令约束、真实拆队与逐格奇袭、现有奇兵调动、归建守恒、接战拆队拒绝、侦察后断粮、配送恢复、指挥接替、人员释放、存档与重置取消、普通军团行军。
- tests/war/battle/encirclement_validation.gd：六面包围、脱离准备、缺口突围、组织损耗与追击。
- tests/war/presentation/xiaopei_battle_validation.gd：18人入军、2万兵力／侧、仅2位主帅请求、前线接战、占格冲突、测试快照恢复。加 -- --capture 输出真实3D截图。
- tests/war/battle/battle_sides_validation.gd：每方有人、主帅属本方、无跨阵营武将；生成将补位、无武将报错、faction_id 优先。只依赖名册与数据，空壳环境也能跑。
- tests/war/battle/tactical_battlefield_validation.gd：六边格绕障、职责服从、预备队受命投入、八日占格、远射与撤退守恒。
- tests/agents/local_agent_validation.gd：原生Ollama请求、关闭思考、结构化响应和本地回退；tests/agents/local_agent_live.gd -- --simulate 另行调用真实本机模型。
