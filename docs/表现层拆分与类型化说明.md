## 一、巨型脚本拆分（第 5 项）

### 做法：分层继承链

三个文件都拆成同目录下一个子文件夹里的若干层，每层 `extends` 上一层（按路径，不依赖全局类缓存），原文件留在原路径、继承最上层：

```
army_world_3d/state.gd → hud.gd → builder.gd → input.gd → animation.gd → army_world_3d.gd
rtk14_world_3d/state.gd → input.gd → builder.gd → frame.gd → rtk14_world_3d.gd
tactical_battlefield/board.gd → targeting.gd → movement.gd → resolution.gd → tactical_battlefield.gd
```

为什么不是静态模块 + 转发（上一轮 campaign_state 的做法）：

- 函数体逐字节搬家，`self`、成员变量、互相调用都不用改写；逆向核对工具保证每个函数块与原文件逐字节相同。
- 所有层是同一个实例，对外成员、信号连接、`scenes/rtk14_world_3d.tscn` 的脚本引用、`GameState.war_presentation`、测试里 `class WorldProbe extends ".../army_world_3d.gd"` 的覆写、`rtk14_reference.gd` 的覆写和 `super._process()`，全部照旧。所以**不需要任何转发**，15 个本地脚本能用到的公开成员一个都没少（见下表）。
- 成员变量仍按下标直接访问；没有经无类型 `w.x` 的间接访问。

约束：下层不能调用上层的函数（GDScript 会报 “not found in base self”）。生成工具会检查调用方向；以后加函数时，放在它调用到的最高一层或更高的层。

各层都是 `@abstract` + `class_name`（不能单独实例化，也不会出现在“新建节点”列表里）。常量与成员变量全部在最底层（state.gd / board.gd），初始化顺序与原来相同。

### 每帧开销

- `_process` 里的代码逐字节没变：没有新增分配、没有新增包装层，成员访问仍是直接下标。
- 唯一变化：对 self 的方法调用在运行时要沿继承链查找方法表，每多一层多一次 StringName 哈希查找（实测约 +1%，见下）。热路径函数集中放在最上层（animation.gd / frame.gd），它们离实例脚本只差一层；调用到 state.gd 的只读查询最多多 5 次查找。
- 实测（沙箱 2 核、无其他负载，headless）：微基准 200 万次调用，单文件与 4 层继承 155–308 ns/次，差异在噪声内。场景内（战斗场景，8 支部队，单挑演出之后）关掉自动处理，直接调用 `army_world._process(1/60)` 与 `rtk14_world_3d._process(1/60)` 各 120 帧为一轮、每次 5 轮，取第 3–5 轮（前两轮是预热）的平均；拆分前（cd3f078）与全部提交后（c15e1e9）交替各跑 3 次，表中取两边的第 2、3 次：

  | | army_world._process | rtk14_world_3d._process |
  |---|---|---|
  | 拆分前 cd3f078 | 303.8 µs/帧（303–305） | 172.8 µs/帧 |
  | 全部提交后 | 306.8 µs/帧（306–308） | 174.0 µs/帧 |
  | 差 | +3.0 µs（约 +1%） | +1.2 µs（约 +0.7%） |

  差值小但稳定（两组区间不重叠），与“沿继承链多几次方法表查找”的预期一致；按 60 帧/秒算，每秒多约 0.25 ms 脚本时间。全部提交后的第 1 次运行与 git 提交操作重叠，受干扰（318 µs），未计入；拆分前 3 次全计入为 304.2 µs，与表中一致。

### 本地合并时注意

- 新增 class_name：上面 34 个，加上表现层 13 个层类名（ArmyWorld3DState/Hud/Builder/Input/Animation、Rtk14World3DState/Input/Builder/Frame、TacticalBoard/Targeting/Movement/Resolution）和 WarStateKeys。本地脚本若有同名 class_name 或全局常量会冲突。

- 新文件没有附 `.gd.uid`，Godot 首次打开会生成。

### 退出泄漏计数 10/2 → 15/7 的结论

`war/presentation/combat_effects_validation` 在沙箱空壳上第 25 行报错中止（本地会正常跑完），中止时它 `new()` 出来的 army_world_3d 实例没有释放，退出时被计为泄漏，连同它的脚本。拆分后这个实例的脚本链多了 5 个层脚本（state/hud/builder/input/animation），所以 “ObjectDB instances leaked” 与 “resources still in use” 各多 5 个。

- 与 class_name 无关：在类型化提交上把 34 个 class_name 全部去掉重跑，仍是 15/7；只含 army_world_3d 拆分的提交已是 15/7。
- 最小复现：`new()` 一个 army_world_3d 不释放直接退出，拆分前 3/1、拆分后 8/6，同样 +5/+5。
- 同一提交重复跑 3 次计数不变。测试输出的其余 35 行、以及另外 40 个测试的输出完全一致，没有运行期行为差异；正常释放的实例不受影响。因此不需要改代码。

## 三、部队模型：去掉主帅、士兵铺满六角格（2026-10-23）

大地图与战斗场景共用 `army_world_3d`，所以两处一起改；`rtk14_reference` 只覆写地图层，检验战场观看界面（`proving/`）是 2D 的，都不涉及部队模型。

### 去掉主帅

- 删除 `state.gd` 对 `army_officer_visual.gd` 的 preload，以及 `OfficerVisual.sync`（builder.refresh）、两处 `OfficerVisual.ground`（builder 适配末尾、animation._process）。
- `_fit_formation_to_hex` 不再读 `CommandOfficers` 节点（签名与包络）。仓库里没有其他代码引用这个节点或该脚本，对外成员一个没少。
- 旗帜、徽章（主将名、头像、战死/被俘）、血条、选中高亮都挂在部队节点和界面层上，不依附主帅模型，未动。
- 该脚本只在你本地（见《缺失脚本新位置对照表》），现在没人引用，本地文件可删；留着也不会被加载。

### 士兵布局

- 每种兵种一份共享布局（`state.gd` 的 `_troop_layout`，第一次用到时算一次，约 6 ms）：
  1. 取站立与行军姿态的包围盒（`troop_rest_bounds`，排除第 9–20 帧交战前刺），乘兵种缩放；
  2. 在格子内切圆（半径 4.05 m）减 `FORMATION_MARGIN`（0.18 m）内，求出士兵连同长枪在**任意朝向**都不出圆的最大椭圆（步兵约 3.30 × 2.55 m 半轴）；
  3. 椭圆内铺交错网格（行距/列距按兵种比例），恰好取 N 个点，多余的从最外圈去掉；
  4. 用最远点采样排序。兵力减少、或镜头拉远降 LOD 时，可见数量取前 n 个，整格均匀变稀，不再只剩前排。
- 每支部队在共享布局上加小抖动（种子是节点名，每帧、每次加载都一样），再整体减均值，满编时站位重心正好在格心。
- 模式：行军把横向收窄到 0.82；交战把每一列往 +Z 前沿压紧。两者都不出椭圆。偏移仍是部队局部坐标，随部队朝向一起旋转。
- 数量：步兵、弓兵 240（原 128），骑兵 80（原 48）；LOD 三档 240/150/75、80/50/26。
- 士兵尺寸：`MODEL_SIZE = 0.62`，约等于原来阵块为了塞进格子被缩到的大小（原适配系数 0.61），所以单个士兵看起来和以前一样大，只是人数多、铺得开。适配系数现在在格心时是 1.0，只在贴城墙、行军跨格时才缩。
- 不越界的口径：站立、行军姿态（含持枪）整体在格内；交战前刺最远会越过格边约 0.5 m（伸向被攻击的邻格），这是接敌动作本身。`hex_combat_presentation_validation` 相应改为检查站立/行军姿态包络。

### 每帧开销

- 适配（`_fit_formation_to_hex`，签名变化时才跑：约每 0.15 s 或 LOD/朝向变化）不再为每个士兵的 8 个角点建包络、也不再建每兵一个字典的 records 数组；兵的包络是“半径 extent 的圆”，用 `HexPresentation.fit_radius` 解析求解，逐兵只写一次变换和渲染包围盒。
- `_face_contact_sectors` 把各前沿方向的坐标变换从“每兵 × 每前沿”提到循环外。
- 实测（同上一节的方法：沙箱 2 核空载、headless、战斗场景 8 支部队，直接调用 `army_world._process(1/60)` 120 帧一轮、5 轮；改动前 6997ad6 与改动后交替各 3 次）：

  | | 第 1 轮（演出中） | 第 2 轮（演出中） | 第 3–5 轮均值（演出结束） |
  |---|---|---|---|
  | 改动前 | 743 µs/帧 | 464 µs/帧 | 310.8 µs/帧 |
  | 改动后 | 543 µs/帧 | 411 µs/帧 | 305.8 µs/帧 |

  前两轮正处在一日演出（3.2 s ≈ 192 帧）里，行军、接敌、适配都在跑，这里人数翻倍反而快了 27% / 11%；后三轮演出已结束，部队静止，差异在噪声内（上次基线 306.8 µs）。注意沙箱里没有弓兵、骑兵模型，8 支部队里只有 4 支步兵真正有士兵。
- 绘制调用：士兵仍是每支部队每兵种一个 MultiMeshInstance3D，人数增加不增加绘制调用。Xvfb 实渲（GL 兼容渲染器，1280×720，同一组镜头）`RENDERING_INFO_TOTAL_DRAW_CALLS_IN_FRAME` 改动前后逐张相同：大地图俯视 130、近景 159，战斗总览 359、俯视 155、近景 187、中景 174；三角形数多 10%（大地图，1 支）到 22–30%（战斗场景，4 支步兵），就是多出来的士兵。

### 验证（沙箱）

- 沙箱缺本地美术（`archer-poses.glb`、`cavalry-poses.glb` 等）和 15 个本地脚本，用空壳顶替，所以只看得到步兵；你本地的主帅模型在沙箱里本来就是空壳，截图只能证明代码里不再创建它。
- 原 `army_pose.gdshader` 在沙箱的 GL 兼容渲染器（llvmpipe）上会让引擎直接崩溃（`Index p_index = 1 is out of bounds (size() = 0)`，改动前后都一样，与本次无关）；截图时在沙箱副本里换成去掉跨姿态混合的版本，仓库里的着色器没动。你本地用 Forward+（Vulkan）不受影响。
- Xvfb 截图（改动前后各 6 张：大地图俯视/近景，战斗总览/俯视/近景/中景）：不再有主帅；士兵铺成接近格子内切圆的椭圆，相邻两格的部队之间留有空隙，无互相穿插。
- `hex_combat_presentation_validation`（只保留步兵的沙箱副本）：12 个朝向、偏心锚点下站立/行军姿态包络都在格内，满编重心在格心，跨格行军 81 步不跳变；适配系数 0.605 → 1.0。
