## 一、巨型脚本拆分（第 5 项）

### 做法：分层继承链

三个文件都拆成同目录下一个子文件夹里的若干层，每层 `extends` 上一层（按路径，不依赖全局类缓存），原文件留在原路径、继承最上层：

```
army_world_3d/state.gd → hud.gd → builder.gd → input.gd → animation.gd → army_world_3d.gd
rtk14_world_3d/state.gd → input.gd → builder.gd → frame.gd → rtk14_world_3d.gd
tactical_battlefield/board.gd → targeting.gd → movement.gd → resolution.gd → tactical_battlefield.gd
```

为什么不是静态模块 + 转发（上一轮 campaign_state 的做法）：

- 函数体逐字节搬家，`self`、成员变量、互相调用都不用改写；逆向核对工具保证每个函数块与原文件逐字节相同。
- 所有层是同一个实例，对外成员、信号连接、`scenes/rtk14_world_3d.tscn` 的脚本引用、`GameState.war_presentation`、测试里 `class WorldProbe extends ".../army_world_3d.gd"` 的覆写、`rtk14_reference.gd` 的覆写和 `super._process()`，全部照旧。所以**不需要任何转发**，15 个本地脚本能用到的公开成员一个都没少（见下表）。
- 成员变量仍按下标直接访问；没有经无类型 `w.x` 的间接访问。

约束：下层不能调用上层的函数（GDScript 会报 “not found in base self”）。生成工具会检查调用方向；以后加函数时，放在它调用到的最高一层或更高的层。

各层都是 `@abstract` + `class_name`（不能单独实例化，也不会出现在“新建节点”列表里）。常量与成员变量全部在最底层（state.gd / board.gd），初始化顺序与原来相同。

### 每帧开销

- `_process` 里的代码逐字节没变：没有新增分配、没有新增包装层，成员访问仍是直接下标。
- 唯一变化：对 self 的方法调用在运行时要沿继承链查找方法表，每多一层多一次 StringName 哈希查找（实测约 +1%，见下）。热路径函数集中放在最上层（animation.gd / frame.gd），它们离实例脚本只差一层；调用到 state.gd 的只读查询最多多 5 次查找。
- 实测（沙箱 2 核、无其他负载，headless）：微基准 200 万次调用，单文件与 4 层继承 155–308 ns/次，差异在噪声内。场景内（战斗场景，8 支部队，单挑演出之后）关掉自动处理，直接调用 `army_world._process(1/60)` 与 `rtk14_world_3d._process(1/60)` 各 120 帧为一轮、每次 5 轮，取第 3–5 轮（前两轮是预热）的平均；拆分前（cd3f078）与全部提交后（c15e1e9）交替各跑 3 次，表中取两边的第 2、3 次：

  | | army_world._process | rtk14_world_3d._process |
  |---|---|---|
  | 拆分前 cd3f078 | 303.8 µs/帧（303–305） | 172.8 µs/帧 |
  | 全部提交后 | 306.8 µs/帧（306–308） | 174.0 µs/帧 |
  | 差 | +3.0 µs（约 +1%） | +1.2 µs（约 +0.7%） |

  差值小但稳定（两组区间不重叠），与“沿继承链多几次方法表查找”的预期一致；按 60 帧/秒算，每秒多约 0.25 ms 脚本时间。全部提交后的第 1 次运行与 git 提交操作重叠，受干扰（318 µs），未计入；拆分前 3 次全计入为 304.2 µs，与表中一致。

### 本地合并时注意

- 新增 class_name：上面 34 个，加上表现层 13 个层类名（ArmyWorld3DState/Hud/Builder/Input/Animation、Rtk14World3DState/Input/Builder/Frame、TacticalBoard/Targeting/Movement/Resolution）和 WarStateKeys。本地脚本若有同名 class_name 或全局常量会冲突。

- 新文件没有附 `.gd.uid`，Godot 首次打开会生成。

### 退出泄漏计数 10/2 → 15/7 的结论

`war/presentation/combat_effects_validation` 在沙箱空壳上第 25 行报错中止（本地会正常跑完），中止时它 `new()` 出来的 army_world_3d 实例没有释放，退出时被计为泄漏，连同它的脚本。拆分后这个实例的脚本链多了 5 个层脚本（state/hud/builder/input/animation），所以 “ObjectDB instances leaked” 与 “resources still in use” 各多 5 个。

## 三、部队模型：去掉主帅、士兵铺满六角格（2026-10-23）

大地图与战斗场景共用 `army_world_3d`，所以两处一起改；`rtk14_reference` 只覆写地图层，检验战场观看界面（`proving/`）是 2D 的，都不涉及部队模型。

### 去掉主帅

- 删除 `state.gd` 对 `army_officer_visual.gd` 的 preload，以及 `OfficerVisual.sync`（builder.refresh）、两处 `OfficerVisual.ground`（builder 适配末尾、animation._process）。
- `_fit_formation_to_hex` 不再读 `CommandOfficers` 节点（签名与包络）。仓库里没有其他代码引用这个节点或该脚本，对外成员一个没少。
- 旗帜、徽章（主将名、头像、战死/被俘）、血条、选中高亮都挂在部队节点和界面层上，不依附主帅模型，未动。
- 该脚本只在你本地（见《缺失脚本新位置对照表》），现在没人引用，本地文件可删；留着也不会被加载。

### 士兵布局

- 每种兵种一份共享布局（`state.gd` 的 `_troop_layout`，第一次用到时算一次，约 6 ms）：
  1. 取站立与行军姿态的包围盒（`troop_rest_bounds`，排除第 9–20 帧交战前刺），乘兵种缩放；
  2. 在格子内切圆（半径 4.05 m）减 `FORMATION_MARGIN`（0.18 m）内，求出士兵连同长枪在**任意朝向**都不出圆的最大椭圆（步兵约 3.30 × 2.55 m 半轴）；
  3. 椭圆内铺交错网格（行距/列距按兵种比例），恰好取 N 个点，多余的从最外圈去掉；
  4. 用最远点采样排序。兵力减少、或镜头拉远降 LOD 时，可见数量取前 n 个，整格均匀变稀，不再只剩前排。
- 每支部队在共享布局上加小抖动（种子是节点名，每帧、每次加载都一样），再整体减均值，满编时站位重心正好在格心。
- 模式：行军把横向收窄到 0.82；交战把每一列往 +Z 前沿压紧。两者都不出椭圆。偏移仍是部队局部坐标，随部队朝向一起旋转。
- 数量：步兵、弓兵 240（原 128），骑兵 80（原 48）；LOD 三档 240/150/75、80/50/26。
- 士兵尺寸：`MODEL_SIZE = 0.62`，约等于原来阵块为了塞进格子被缩到的大小（原适配系数 0.61），所以单个士兵看起来和以前一样大，只是人数多、铺得开。适配系数现在在格心时是 1.0，只在贴城墙、行军跨格时才缩。
- 不越界的口径：站立、行军姿态（含持枪）整体在格内。（当时交战前刺最远越过格边约 0.5 m；第四节已修掉，交战姿态包络重新纳入测试。）

## 四、接触战斗动画：性能与观感（2026-10-23）

纯表现层：战斗结算、存档、主动技能/战法/怒气都不涉及。

### 性能

- **小兵朝向搬进着色器**。原来 `_face_contact_sectors` 每 0.05 s 对每个士兵 `get/set_instance_transform` 和 `custom_data`（240 兵 × 每个前沿）。现在每支部队把至多 `MAX_FRONTS`（4）个前沿的世界朝向、上一组朝向、切换时刻和阵心作为材质参数（每个编队本来就有自己的材质副本，不会互相覆盖），`army_pose.gdshader` 按实例脚下位置选最近前沿，按 `animation_clock` 以 `SOLDIER_TURN_RATE`（3.5 rad/s）插值转身，绕脚下中心旋转。
  - 同一朝向的转身中途换目标：从当前朝向续接（CPU 能算出所有兵共同的当前朝向）。多前沿转身未完成时，新集合等转完再换，不会跳变。
  - 交战力度（原 `custom_data.b`）在着色器里由同一个点积算出。
  - 前沿集合不变时 CPU 每帧零 MultiMesh 写入；`facing_revision` 仍随集合变化递增（仓库里只有适配签名读过它，现在签名已不含它）。
  - 实例不再带朝向旋转，适配的渲染包围盒按任意朝向 + 前排推进量计算。
  - `_soldier_transform(group, batch, i)` 是着色器的 CPU 镜像（朝向 + 推进，不含受击后仰与倒地），测试通过它读朝向和包络。
- **交战读数缓存**。`_combat_visual` 与前沿列表缓存在 `combat_cache` / `combat_fronts_cache`，只在 tick、演出状态、battle_test 或任一部队位置变化时重算（每帧只比较一组位置）；`refresh()`、`begin_day()` 作废。`_process`、喊话、伤亡判定读缓存，命中时不分配。测试直接调用的 `_combat_visual`、`_combat_fronts` 仍现算。
- **特效对象池**。`combat_effects_3d` 的扫击/火花/尘土/箭矢在 `end_frame` 里隐藏后进 `contact_pool`，新接触按形状（近战/远射、野战/城头）取回；`contacts` 仍只含当前接触。扫击参数与火花尘土颜色只在值变化时下发；`animation_clock` 暂停时不下发。
- **格号与兵数档位只在变化时重算**。`_formation_cell` 把部队脚下的格号缓存在编队上，位置 xz 变了才重新 `grid().pick()`（每次构造并测试最多 9 个六角形，原来每帧每支部队一次）；`_apply_troop_detail` 在 LOD 档位与兵力比例都没变、且没有阵亡兵还在倒地时不再逐批次走 `_show_troops`，`refresh()` 重设模型数后以 `force` 调用照常校正。
- **着色器去掉 uniform 除数的整数 `%`、`/`**（改为比较与浮点除法）。这是第三节提到的沙箱 GL 兼容渲染器崩溃（`Index p_index = 1 is out of bounds`）的根因：llvmpipe 在无 AVX 的 CPU 上为它们生成非法指令（最小复现：只含 `(pose_start + 3) % pose_count` 的着色器即崩，常量除数、`texelFetch`、`textureSize`、float `mod` 都不崩）。现在沙箱里直接用仓库着色器截图，不再需要替换副本。

实测（沙箱 2 核、headless、战斗场景 8 支部队；交战场景在沙箱里人为布置 3 组近战接触：一支被两路夹击，共 5 支交战、6 个接触，镜头对准；`army_world._process(1/60)` 直接调用，120 帧一轮 × 5 轮，空载取第 3–5 轮，交战取 5 轮；改动前 58e82a2 与本节最终代码交替各 3 次，取 3 次的中位数。复测时另一核在跑全套校验，交战第 3 次改动后被拖到 475，差异远大于这个噪声）：

| | 空载 µs/帧 | 交战 µs/帧 | MultiMesh 写入/帧（交战稳态） | 材质参数写入/帧（交战） |
|---|---|---|---|---|
| 改动前 58e82a2 | 303（302–338） | 1974（1970–1975） | 0（另每 3 帧读 240×2） | 20 |
| 只做朝向/缓存/对象池（0a038eb、d087c7a，上一次测） | 284 | 508 | 0 | 18 |
| 本节最终 | 192（191–193） | 428（412–475） | 0 | 18 |

交战约降到 1/4.6，空载降 37%。空载的下降主要来自格号缓存与兵数档位跳过（剖析见下）。

- 绘制调用：士兵仍是每支部队每兵种一个 MultiMeshInstance3D；对象池里隐藏的特效不绘制。Xvfb 实渲（GL 兼容，1280×720，同一组镜头）`TOTAL_DRAW_CALLS_IN_FRAME`：接触近景 135 → 136（多出的是常驻对象池里的一个特效节点），俯视 169 → 169；伤亡宽镜头 141 → 145（倒地窗口内，结束后两边都是 137）。
- MultiMesh 写入：稳态（无转身、无伤亡）前后都是 0；区别在读——改动前每 3 帧对每个交战部队读 240 个变换 + 240 个 custom_data，现在不读。伤亡时只写倒下那几个兵的 custom_data。

### 观感（全部在着色器里，CPU 只在状态变化时写几个材质参数）

- **前排压上**：交战时（`contact_window` 记开始/结束时刻，0.5 s 渐入、0.6 s 渐出）小兵沿朝向到本格内切圆的距离（左右各偏半个最宽姿态宽度 `lunge_width` 取较小值）减去前刺长度 `lunge_reach` 和 `CONTACT_GAP`（0.2 m）就是可前压的量；离边 `CONTACT_PUSH_BAND`（2.2 m）以内的前排按距离渐变前压，后排不动。
- **前刺不越界**：同一公式里可前压量为负时（前刺会越过格边）立即后收，不等渐入。交战姿态包络恢复为测试检查（`hex_combat_presentation_validation`：6 个方向接敌、全部交战姿态角点都在本格内）。代价：长枪前刺约 2.0 m，最前沿的兵会后收（沙箱步兵：90 兵前压最多 0.56 m，81 兵后收最多 1.21 m），整条前线停在枪尖碰到格边前 0.2 m。
- **错开出手**：交战姿态相位仍是每兵随机（`custom_data.r`，0–1 × 帧数），速率差从 ±8% 加大到 0.8–1.2 倍，再按前后排（`custom_data.b`，布阵时的前排度）乘 0.82–1.18：前排出手更勤。弓兵不变（箭矢按弓兵速率同步）。
- **受击后仰**：被敌方近战前沿攻击（`under_attack`）的前排，在以交战周期、与自己出手错开 0.37 周期的节拍上后仰约 8° 并后退 0.14 m。
- **阵亡倒地**：兵力下降使可见士兵减少时（LOD 换档不算），减掉的那几个兵不立即隐藏：`custom_data.a` 记死亡时刻（`-(t - death_epoch) - 10`，数值保持很小以免半精度失真），着色器 0.5 s 内倒下（贴地下沉 0.05 m；步兵后仰 1.5 rad 再按相位向左或右侧倒 0.45 rad，骑兵按相位向左或右侧倒），在地上停到 1.7 s，1.7–2.5 s 下沉 0.7 m 并抖动淡出（屏幕门 discard，不进透明管线），`FALL_SECONDS`（2.6 s）后才真正减少可见数。倒下的兵按倒地程度染成暗血红（0.75 混合）。倒下时刻对齐当天演出：行军接敌的部队在抵达后 0.25 s 开始，按 `LOSS_COUNT_SECONDS` 在 1 s 内陆续倒下，和徽章兵力数字同步。
  - 为什么要染色：可见数取最远点采样布局的前 n 个，阵亡的是这个顺序的尾部，在阵内均匀散开，倒下后大多被站立的兵遮住，截图里只露出枪杆（临时把倒地兵染成纯红定位过）。只压暗的话会融进阵型自己的阴影；暗红在灰白兵群和褐色地面上都分得出来。要让“前排先倒”，得在倒下时交换实例数据（变换、颜色、custom_data），这次没做。
  - 代价：倒地兵多画约 1.2 s；同一宽镜头倒地窗口内绘制调用 145（改动前 141），倒地结束回到 137。
